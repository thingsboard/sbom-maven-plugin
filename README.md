# sbom-maven-plugin

Maven plugin that post-processes the CycloneDX SBOM generated by `cyclonedx-maven-plugin`:

- `merge` folds a CycloneDX SBOM embedded in a dependency into the project's SBOM.
- `metadata` sets who makes and supplies the software and the SBOM.
- `package` writes one SBOM per distribution package (`.deb`, `.rpm`, `.zip`), next to the package file.
- `image` writes the SBOM of every architecture of a pushed Docker image and attaches it to the image: what Syft finds in the image, with the parts we built replaced by our own SBOMs.

ThingsBoard uses it to fold the npm SBOM of the Angular UI (`ui-ngx`, generated with `cyclonedx-npm`) into the Maven SBOM of the server application (generated with `cyclonedx-maven-plugin`). The result is one SBOM per shipped artifact, with the npm packages attached to the `ui-ngx` component in the dependency graph.

## merge goal

```xml
<plugin>
    <groupId>org.thingsboard</groupId>
    <artifactId>sbom-maven-plugin</artifactId>
    <version>1.0.0</version>
    <executions>
        <execution>
            <goals>
                <goal>merge</goal>
            </goals>
            <configuration>
                <host>org.thingsboard:ui-ngx</host>
            </configuration>
        </execution>
    </executions>
</plugin>
```

The `merge` goal runs at `process-resources` by default, after `cyclonedx-maven-plugin:makeBom` bound to `generate-resources`.

| Parameter | Property | Default | Description |
| --- | --- | --- | --- |
| `host` | `sbom.merge.host` | required | `groupId:artifactId` of the runtime dependency that carries the nested SBOM |
| `resource` | `sbom.merge.resource` | `META-INF/sbom/<artifactId>.cdx.json` | Path of the nested SBOM inside the host jar or classes directory |
| `targetFile` | `sbom.merge.targetFile` | `${project.build.outputDirectory}/META-INF/sbom/application.cdx.json` | SBOM to merge into, rewritten in place |
| `skip` | `sbom.merge.skip` | `false` | Skip the merge |

## metadata goal

```xml
<execution>
    <id>sbom-metadata</id>
    <goals>
        <goal>metadata</goal>
    </goals>
    <configuration>
        <manufacturer>
            <name>ThingsBoard, Inc.</name>
            <urls>
                <url>https://thingsboard.io</url>
            </urls>
            <contacts>
                <contact>
                    <email>security@thingsboard.io</email>
                </contact>
            </contacts>
        </manufacturer>
        <supplier>...</supplier>
        <componentManufacturer>...</componentManufacturer>
    </configuration>
</execution>
```

| Parameter | Sets | Meaning (CycloneDX 1.6) |
| --- | --- | --- |
| `manufacturer` | `metadata.manufacturer` | The organization that created the SBOM |
| `supplier` | `metadata.supplier` | The organization that supplies the software the SBOM describes |
| `componentManufacturer` | `metadata.component.manufacturer` | The organization that created the software the SBOM describes |
| `timestamp` (`sbom.metadata.timestamp`) | `metadata.timestamp` | When the SBOM was made. Default: `${project.build.outputTimestamp}` |

`timestamp` is a date and time with an offset (`2026-01-31T12:00:00Z`) or seconds since 1970, and is written in UTC. `cyclonedx-maven-plugin` leaves the timestamp out of the SBOM when Maven builds reproducibly, that is when `project.build.outputTimestamp` is set; the goal puts that time back, so set the property to the time of the release when you set the release version. Without it, or with the `1980-02-01T00:00:00Z` that newer Maven versions set by themselves, the timestamp of the SBOM stays as it is. The `package` goal copies the timestamp of the application SBOM, and the `image` goal that of the first component with an `sbom`.

Each of the first three is an organization with a `name`, optional `urls` and optional `contacts` (`name`, `email`, `phone`). Configured fields replace existing values; fields that are not configured are left as they are. Also takes `targetFile` (`sbom.metadata.targetFile`) and `skip` (`sbom.metadata.skip`).

The build fails, and the file is left untouched, when nothing is configured, the timestamp is not a date and time with an offset, an organization has no name, a url is blank, a contact is empty, the SBOM is older than CycloneDX 1.6, the input or the result fails schema validation, or anything other than these fields would change.

## package goal

```xml
<execution>
    <id>package-sbom</id>
    <goals>
        <goal>package</goal>
    </goals>
    <configuration>
        <name>thingsboard</name>
        <packages>
            <package>
                <id>deb</id>
                <file>${project.build.directory}/thingsboard.deb</file>
                <purl>pkg:deb/thingsboard/thingsboard@${project.version}-1?arch=all</purl>
                <skip>false</skip>
            </package>
        </packages>
        <components>
            <component>
                <sbom>${project.basedir}/src/main/sbom/gateway-management-extension.cdx.json</sbom>
                <file>${project.build.directory}/data/resources/js_extensions/gateway-management-extension.js</file>
            </component>
            <component>
                <type>cryptographic-asset</type>
                <name>DigiCert Global Root G2</name>
                <file>${project.build.directory}/data/certs/azure/DigiCertGlobalRootG2.crt.pem</file>
            </component>
            <component>
                <type>application</type>
                <group>com.sun.winsw</group>
                <name>winsw</name>
                <version>2.0.1</version>
                <purl>pkg:maven/com.sun.winsw/winsw@2.0.1?classifier=bin&amp;type=exe</purl>
                <license>MIT</license>
                <file>${project.build.directory}/windows/service.exe</file>
                <packages>
                    <package>zip</package>
                </packages>
            </component>
        </components>
    </configuration>
</execution>
```

The `package` goal runs at `package` by default. Declare the plugin after the plugins that build the packages, so it runs after them in the same phase. For each package that is not skipped it writes `<package file>.cdx.json` next to the package, once every package has been checked:

- The package is the root component (`metadata.component`): the configured `name`, `version` and `purl`, the SHA-256 and SHA-512 of the package file, and the description, licenses, manufacturer and website of the application.
- The application SBOM's root and all its components and dependencies are kept unchanged; the package depends on the application.
- Each bundled component the package contains is added, and the package depends on it. A file gets its SHA-256 and SHA-512; a directory gets no hashes. A `cryptographic-asset` must point to an X.509 certificate, whose subject, issuer and validity are added as `cryptoProperties`.
- A bundled component with an `sbom` takes everything from that SBOM instead of the configuration: its root becomes the component, and its components and dependencies are added under it. The SBOM must give the SHA-256 of `file`, and it must match the file being packaged, so a file copied without its SBOM, or with an SBOM from another build, fails the build. Components already in the application SBOM with the same `bom-ref` and `purl` are not added twice. Its tools are added to `metadata.tools`.
- `metadata.tools`, `lifecycles`, `manufacturer` and `supplier` are copied from the application SBOM. The `serialNumber` is derived from the package purl and contents.

| Parameter | Property | Default | Description |
| --- | --- | --- | --- |
| `packages` | | required | Packages to describe: `id`, `file`, `purl`, optional `skip` |
| `components` | | none | Bundled components: `type` (default `library`), `group`, `name`, `version`, `description`, `purl`, `cpe`, `license` (SPDX expression), `supplier` (`name`, `urls`, `contacts`), `file`, `sbom` (CycloneDX SBOM of `file`; replaces all the other details), `packages` (ids of the packages that contain it; all when empty) |
| `name` | `sbom.package.name` | `${project.artifactId}` | Name of the package component |
| `version` | `sbom.package.version` | `${project.version}` | Version of the package component |
| `sourceFile` | `sbom.package.sourceFile` | `${project.build.outputDirectory}/META-INF/sbom/application.cdx.json` | Application SBOM to start from |
| `skip` | `sbom.package.skip` | `false` | Skip all packages |

The build fails, and no package SBOM is written, when package ids repeat, a package has no purl or an invalid one, a package file is missing or empty, a bundled component has no name, is declared twice, has an `sbom` together with details of its own or without a `file`, sets `installDir` or `bundleDir`, still contains an unresolved `${...}` property, has a supplier without name or with a blank url, has an `sbom` that is invalid, uses another spec version, has components its root does not depend on, or does not match the file's hashes, refers to an unknown package id, points to a missing file or an empty directory, or clashes with a component already in the SBOM, a `cryptographic-asset` is not an X.509 certificate, a `cpe` does not start with `cpe:2.3:` or `cpe:/`, or the result fails schema validation or loses a dependency path of the application.

## image goal

```xml
<execution>
    <id>image-sbom</id>
    <phase>post-integration-test</phase>
    <goals>
        <goal>image</goal>
    </goals>
    <configuration>
        <repository>thingsboard/tb-node</repository>
        <tags>
            <tag>latest</tag>
            <tag>${project.version}</tag>
        </tags>
        <scanExclude>/usr/share/thingsboard/**</scanExclude>
        <components>
            <component>
                <sbom>${main.dir}/application/target/thingsboard.deb.cdx.json</sbom>
                <file>${project.build.directory}/thingsboard.deb</file>
            </component>
        </components>
    </configuration>
</execution>
```

The `image` goal has no default phase: bind it after the build pushes the image, because it reads the image from the registry. For every architecture of the pushed image it:

1. finds the digest of that architecture's image with `docker buildx imagetools inspect --raw`, for each of the `tags`. Tags that point to the same image share one SBOM;
2. scans the image with `syft scan registry:<repository>@<digest>`, leaving out `scanExclude`;
3. writes the image SBOM to `<outputDirectory>/<namespace>_<name>_<version>_<architecture>_<first 12 digits of the digest>.cdx.json`;
4. attaches the SBOM to that architecture's image as an OCI referrer artifact of type `application/vnd.cyclonedx+json` with `oras attach`, unless `oras discover` finds one there.

Nothing is attached unless the SBOM of every architecture is written. An image that has a CycloneDX SBOM attached already keeps it and gets no second one, so when attaching fails part-way, the images attached so far keep their SBOMs and running the build again attaches the rest.

It needs `docker` with buildx, [`syft`](https://github.com/anchore/syft) and [`oras`](https://oras.land) on the `PATH`, logged in to the registry as for `docker push`. The image must be a multi-architecture one, pushed with `docker buildx build --platform`.

To see what is attached to an image: `oras discover thingsboard/tb-node@sha256:40c3...`.

The result describes the image as a `container` root component (`pkg:docker/<namespace>/<name>@<digest>?arch=<architecture>`, with `&repository_url=<registry>` when the image is not on Docker Hub; version = `version`, SHA-256 = digest) that depends on everything in it:

- Everything the scan found is kept unchanged, except what the bundled components replace. The scan's own root is dropped; the image depends on the scanned components nothing else depends on, and on one component of each dependency cycle nothing outside the cycle depends on.
- Each bundled component is added with its SBOM, as in the `package` goal, and the image depends on it. Its tools are added to `metadata.tools`; `lifecycles`, `manufacturer`, `supplier` and the root's manufacturer come from the first bundled SBOM.
- The `serialNumber` is derived from the image purl, so each architecture's SBOM has its own.

A bundled component with an `sbom` says how its SBOM is checked against the image with exactly one of:

| Anchor | For | Check |
| --- | --- | --- |
| `file` | A package the image installs, e.g. `.deb` | The SBOM must give the SHA-256 of `file`, as in the `package` goal. When its root is a `deb`, `rpm` or `apk` package, the scan must list exactly one installed package with that purl type and name, and with the version of the SBOM's purl; it is replaced by the SBOM's root and keeps the dependencies the scan found (e.g. on the JRE). Exclude the package's install directory from the scan with `scanExclude`: the build fails when the scan lists any component of the SBOM. |
| `installDir` | An npm application installed in the image by `yarn install` | Everything the scan found under the directory must be in the SBOM at the same path (`cdx:npm:package:path`) and version, or be an optional package without a path that matches by purl; it is replaced by the SBOM's component. Every required package must be installed at each of its paths. Optional packages (`scope: optional`) the image does not have are dropped with their dependencies, so platform-specific packages listed for every platform (`yarn-sbom.js --all-platforms`) keep only the ones this architecture installs. The scan's entry for the application's own `package.json` is replaced by the SBOM's root. Do not exclude the directory from the scan. |
| `bundleDir` | Prebuilt files copied into the image, e.g. a web UI bundle | Everything the scan found under the directory must be in the SBOM by purl; it is replaced by the SBOM's component. The SBOM may list more, since bundled code has no files per package. |

Scanned components are claimed by the most specific directory, so a `bundleDir` can sit inside an `installDir`. A component outside every directory stays a component of the scan, even when a bundled SBOM lists the same purl: base images often ship their own copy of a package.

A bundled component without an `sbom`, such as a browser an install script downloads, is added from its configuration as in the `package` goal; `file` is optional.

| Parameter | Property | Default | Description |
| --- | --- | --- | --- |
| `repository` | `sbom.image.repository` | required | `<namespace>/<name>` of the image, without tag. Docker Hub is the registry unless one comes first: `registry.example.com/<namespace>/<name>` |
| `tags` | `sbom.image.tags` | `${project.version}` | Every tag the build pushed; blank tags are ignored |
| `version` | `sbom.image.version` | `${project.version}` | Version of the image component |
| `plainHttp` | `sbom.image.plainHttp` | `false` | Talk to the registry over plain HTTP, for a local test registry |
| `scanExclude` | `sbom.image.scanExclude` | | Glob of the image paths Syft must not scan |
| `outputDirectory` | `sbom.image.outputDirectory` | `${project.build.directory}/sbom` | Where to write the scans and the image SBOMs |
| `components` | | required | Bundled components, as in the `package` goal without `packages`, plus `installDir` and `bundleDir` (absolute paths in the image); `@{architecture}` in a version, purl or cpe stands for the architecture of the image |
| `attach` | `sbom.image.attach` | `true` | Attach the SBOMs to the image; `false` only writes them |
| `docker`, `syft`, `oras` | `sbom.image.docker`, `sbom.image.syft`, `sbom.image.oras` | `docker`, `syft`, `oras` | The executables to run |
| `skip` | `sbom.image.skip` | `false` | Skip the image SBOMs |

The build fails, and nothing is attached, when the repository is not `<namespace>/<name>` after the optional registry, no tag is configured, `docker`, `syft` or `oras` is missing or fails (the message of the tool is reported), a tag is not a multi-architecture image with Linux images, an architecture is not lowercase letters and digits, the version is blank, no components are configured, a component has no name, is declared twice, has an `sbom` together with details of its own, sets `packages`, or has a supplier without name or with a blank url, a component with an `sbom` sets none or more than one of `file`, `installDir` and `bundleDir`, a component without an `sbom` sets a directory, a directory is not absolute or ends with `/`, a value still contains an unresolved `${...}` property, the scan does not list a `file` package exactly once or lists it with another version, the scan lists a component of a `file` component's SBOM, the image has a component without a purl under a directory, or a package that the SBOM does not list or lists with another version, a required package is not installed at its path or has no path, components clash, the result fails schema validation, or a component is not reachable from the image.

## Skipping

`-Dsbom.skip=true` skips every goal of the plugin, whatever the `skip` of a goal says. A build that makes SBOMs only on request sets the `sbom.skip` property to `true` in the POM and runs with `-Dsbom.skip=false`, or in a profile that sets it to `false`, when it needs them.

## What the merge does

- Appends the nested components and their dependency graph to the target SBOM.
- Replaces the nested SBOM's root (`metadata.component`) with the host component, so the host depends on the nested root's direct dependencies.
- Adds the nested SBOM's tools to `metadata.tools.components`.
- Keeps the target's `serialNumber`, `version` and `metadata.component`.

## Checks

The build fails, and the target file is left untouched, when any of these does not hold:

- Both inputs are CycloneDX JSON with the same `specVersion` and pass schema validation (`cyclonedx-core-java`).
- Both inputs have unique bom-refs and every dependency reference resolves.
- The target has exactly one component whose purl starts with `pkg:maven/<groupId>/<artifactId>@`.
- The nested root has direct dependencies and is not itself listed as a component.
- A bom-ref present in both inputs belongs to identical components.
- The merged SBOM passes schema validation, keeps the target's identity, contains exactly the union of both inputs' components, and every nested component is reachable from the host.

## Building

```
./mvnw verify
```

`./mvnw test` runs the unit tests, which need no Docker. `verify` also runs two kinds of integration tests:

- `*IT` classes in `src/test/java`, run by Failsafe, validate merged, package and image SBOMs with the official `cyclonedx-cli` in Docker (Testcontainers). They are skipped when Docker is not available, and with `-DskipITs`. `RegistryImageIT` runs what the `image` goal does with the real `docker buildx`, `syft` and `oras` against a registry in Docker: it is also skipped when `syft` or `oras` is not installed or Docker cannot push a two-architecture image, except in CI, which installs the versions pinned in `.github/workflows/build.yml`.
- The projects in `src/it`, run by Invoker, build small projects with the plugin and `cyclonedx-maven-plugin`. The `image` goal runs there with the stand-ins for `docker`, `syft` and `oras` in `src/it/stubs`. They are skipped with `-Dinvoker.skip`.

## Releasing

Releases are deployed to `https://repo.thingsboard.io/artifactory/libs-release-public` by the release manager, whose `~/.m2/settings.xml` holds the credentials of the `thingsboard-repo-deploy` server. From an up-to-date `main`:

```
./release.sh 1.0.0 1.0.1-SNAPSHOT
```

The next development version is optional and defaults to the next patch version. The script stops at the first failure, and:

1. Runs `release:prepare` on a new `release/1.0.0` branch, without pushing. It commits `1.0.0`, with `project.build.outputTimestamp` set to the current time, tags that commit `v1.0.0`, then commits `1.0.1-SNAPSHOT`.
2. Pushes the branch, opens a PR and waits for its checks.
3. Merges the PR once the checks pass. `main` takes only merge commits, so the tagged commit stays in its history.
4. Pushes the tag, then runs `release:perform`: builds the tag in `target/checkout` and deploys it.
5. Creates the GitHub Release `v1.0.0` with generated notes and the plugin jar.

The release builds skip the tests, since CI has run them on the PR.

If the script stops, its last message says what to do:

- **Start over** when it stops before the PR is merged: nothing is published yet. Close the PR if one was opened, run `git switch --discard-changes main`, then delete the `release/1.0.0` branch (locally and on GitHub) and the local `v1.0.0` tag.
- **Finish the release by hand** when it stops after the PR is merged. From the same clone, run the steps that have not run yet:

  ```
  git fetch origin main && git merge-base --is-ancestor v1.0.0 origin/main   # must succeed: else don't push the tag, start over
  git push origin v1.0.0
  ./mvnw release:perform
  gh release create v1.0.0 --verify-tag --generate-notes --title v1.0.0 target/checkout/target/sbom-maven-plugin-1.0.0.jar
  git switch main && git pull --ff-only && git branch --delete release/1.0.0
  ```

  Once `release:perform` has deployed, the version is in Artifactory and cannot be deployed again.

Every commit sets `project.build.outputTimestamp`, so any of them, release tags included, can be rebuilt into identical artifacts.
